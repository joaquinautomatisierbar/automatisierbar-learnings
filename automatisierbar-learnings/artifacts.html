// 01 — was ein artifact ist

Kein neues Tool. Eine bessere Output-Form.

Normaler Chat ist Text. Ein Artifact ist Text plus Form — es rendert, ist klickbar, lebt in einem eigenen Panel und bleibt im Gespräch erhalten. Du kannst später draufzeigen und sagen "ändere das" — ohne neu zu erklären.

Was rein passt

html / react
Interaktive Tools

Rechner, Mockups, kleine Apps, Demos.

mermaid / svg
Diagramme

Prozess-Maps, Flows, Architektur.

markdown / pdf
Dokumente

Reports, Referenzen, Handouts.

code
Längere Skripte

n8n-Snippets, Flask-Routen, Configs.

Der eine Punkt, den du behalten solltest: ein Artifact ist billig zu erzeugen und billig wegzuwerfen. Das ist seine Stärke — nicht Perfektion, sondern Geschwindigkeit beim Zeigen.

// 02 — wann es echten hebel hat

Wenn jemand etwas sehen muss, bevor es gebaut wird.

Das ist exakt deine Prototype Testing-Phase. Ein Artifact sitzt zwischen "Idee" und "in n8n gebaut" — der Moment, wo du Reaktion testen willst, ohne schon echte Arbeit investiert zu haben.

  • Client-Mockup vor dem Bau. Bevor du eine n8n-Automation für Bieri oder Gränacher baust — ein klickbares HTML-Mockup des Outputs. Zeigt's der Kunde, du siehst die Reaktion in 5 Minuten statt nach 5 Stunden Bau.
  • Rechner fürs Sales-Gespräch. Ein ROI-Rechner, den Nico im Walk-in live aufmacht: Stunden rein, Ersparnis raus. Wiederverwendbar, kein Bau pro Kunde.
  • Prozess-Map während des Workflow-Interviews. Mermaid-Diagramm des Kundenprozesses, live mitgezeichnet — macht Engpässe sichtbar im Gespräch.
  • Schnelle interne Referenz. Ein One-Pager fürs Team, wenn es kein druckreifes PDF sein muss — schneller iterierbar als deine Playwright-PDF-Pipeline.
// decision filter — bevor du ein artifact baust
  • Muss es jemand sehen oder anfassen, nicht nur lesen? → ja, Artifact.
  • Reicht eine Wegwerf-Version, um Reaktion zu testen? → ja, Artifact.
  • Wird es mehrfach gebraucht (Rechner, Mockup-Vorlage)? → ja, lohnt sich.
// 03 — wann es das falsche werkzeug ist

Artifacts sind die Kommunikations-Schicht. Nicht die Infrastruktur.

Der häufigste Fehler wäre, sie mit deiner echten Stack zu verwechseln. Klare Trennung:

echte Automation, läuft 24/7
✗ kein Artifact → das ist n8n
deployte App mit State & Daten
✗ kein Artifact → das ist Flask auf Render
Antwort passt in 2 Sätze
✗ kein Artifact → einfach Text
Kunde soll Output anschauen
✓ Artifact → Mockup / Demo
Team braucht ein Live-Tool
✓ Artifact → Rechner / Referenz

Reality-Check: Ein Artifact läuft nur, solange das Chat-Fenster offen ist. Es hat keinen echten Server, keine Datenbank, keine Persistenz für deine Kunden. In dem Moment, wo etwas produktiv laufen muss, ist es ein n8n-Workflow oder die Flask-App — nicht ein Artifact. Verwechselst du das, baust du Spielzeug, wo Infrastruktur hingehört.

Merksatz: Artifact = zeigen, testen, wegwerfen. n8n / Flask = bauen, deployen, betreiben.

// 04 — anwendung auf dein setup

Drei Stellen, wo es sofort Sinn macht.

1 · Bieri / Gränacher — Mockup statt Beschreibung

Nico präsentiert gerade. Statt den automatisierten Dossier-Flow zu beschreiben, lass mich ein klickbares HTML-Mockup bauen: "gescannte Post → Dossier abgelegt → Mail an Klient". Der Anwalt sieht den Output, nicht eine Erklärung. Kostet einen Prompt, kein Bau-Risiko.

2 · ROI-Rechner fürs Outreach-Team

Ein Artifact, das Nico, Tej und Patrik im Gespräch öffnen: Stundenlohn + Stunden/Woche manuelle Arbeit rein, Jahres-Ersparnis raus. Einmal gebaut, immer wieder benutzt. Genau dein "wiederverwendbar statt einmalig"-Prinzip. → Scroll runter, der Prototyp davon ist unten drin.

3 · Workflow-Interview → Prozess-Map

Während oder direkt nach dem Interview: ich gieße den beschriebenen Prozess in ein Mermaid-Diagramm. Du siehst Schwarz auf Weiß, wo die manuellen Schritte und Workarounds sitzen — bevor irgendwer ans Process Mapping in Notion geht.
